## Added afterward, in order

1. As part of testing, use real (non-synthetic) voice clips and poor-quality recordings; simulate them arriving from multiple sources at different loudness and clarity; simulate a person moving away from their computer so another source is louder, and make sure the speaker is still identified correctly. Test everything thoroughly, not one test and done.
2. Simulate connection differences where a voice reaches the server later, and make sure it syncs properly with various amounts of lag.
3. Make sure there is good logic around sending requests to agents that are already handling certain kinds of work in a single repo, rather than splitting requests between agents. They'll be smarter with context if they keep handling similar work.
4. The split and bento views can show the canvas (following whichever user or agent makes sense to follow), a Chromium window (reference designs we asked for, or the dev servers hosted on the host), or windowed screen casting where client computers share their screens (with permission granted on the client device in the app).
5. Screen sharing works both directions: the host's main brain can request it, or someone can push it up and the main brain finds a place for it.
6. The brain on the host has complete control through tools to arrange things and make its own presentation layouts in the app.
7. A good, premium-feeling annotation system: people put pins on the canvas and on the shared (host-hosted) dev server view. Annotations are app-wide, and all of them together get sent as one prompt to the main brain to divvy out.
8. Users can prompt the brain directly by typing a prompt in JamSesh or by recording one. It's already recording unless muted; recording marks the time between pressing Record and Stop and sends it specifically as a prompt for the main brain, the same way saying "hey jamsesh" would.
9. Recording also watches the user's cursor position on screen, seeing where they point and converting it into context: essentially annotations for the prompt. (Inspiration: the owner's "cursor cap" project.)
10. The main brain can be given any name, and it listens for that name.
11. The main brain adapts to user feedback about its demeanor and the way it handles things.
12. Users can mute their audio at any time.
13. Users' agents can set their handler's name and their own name, so names are clear.
14. Users can share their camera, so there's a camera stream (or just a photo) as the user's profile picture.
15. A user's position or title is part of their profile, so the main brain can tie it all together.
16. The main brain does a good job on every piece of incoming data: sorting it, storing what should be context, taking what should be a prompt, and doing both persistent context curation and divvying out tasks.
17. Good autosave; the main brain can save all the canvas work, context, layouts, and so on.
18. Works equally well with everyone in the same room, everyone remote, or a group in person with some people remote.
19. Users can navigate between canvas pages, with good logic for when it makes sense to make a new page.
20. Solid logic for when the AI talks out loud: it shouldn't feel unresponsive, but it shouldn't respond to everything like a typical voice mode. Get the balance right.
21. Visual polish: no buttons wrapping to two lines, nothing cut off; simplify to icons where really necessary; if it looks broken, fix it.
22. Setup: how is it decided that a machine is the host versus a client? No default public server (FigCraft has one; JamSesh must not). Make it extremely easy, and secure, to make the host reachable from anywhere over the internet with a DDNS like DuckDNS.
23. An honest opinion on whether a git OAuth for the host (so the brain can pull every repository in a session into its own environment, per project or session) is worth it.
24. Keep the host machine awake for as long as people are connected, if it isn't already. If it's already kept awake, never undo that.
25. No scripts for people to run. Instead: a QR code that fully sets up and connects when fed into Claude Code or Codex; under it, the address and a large 4-character code usable in the agent or in the app on a client device. The code refreshes about every 30 seconds, authenticator-style.
26. No point using the app locally without being connected. But: graceful connection recovery, a local saved state with smart merge when someone loses connection and reconnects, and local memory of their identity for each session they've been in.
27. Agents communicate with each other through the server and ask each other questions; the main brain instructs them to work together and compare work.
28. The client is a real desktop app (a Mac app), not only a browser page; the browser stays as an option, and there's a great mobile version that runs well in a phone browser.
29. The host app has real control over its machine: it can compile a preview desktop app, use the iPhone Simulator, and arrange things on screen even outside the app. Setup makes granting the needed macOS permissions really user friendly.
30. Connecting Claude Code or Codex is as simple as saying "connect to jamsesh" when the app is open on the same computer.
31. The host brain can put up the connection QR code and 4-character code nice and big when someone asks, plus how to join on a phone.
32. The brain knows the resolution and aspect ratio of the displays it runs on, and plans in-app and out-of-app layouts accordingly.
33. Host builds requested by agents are approved by a person, and approval is fully controllable by voice, because often nobody is at the host machine.
