## Production findings

1. **Must fix — an old approval can replace a newer person’s lock.** [session.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/session.ts:1660) records who owned the lock when an agent asks, but [answerShowRequest](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/session.ts:1687) never checks that the same lock still exists. Approval calls `showReady`, which uses `override: true`. If Chey is asked, Felipe then casts to that screen, and Chey answers the still-pending question, the agent’s item replaces Felipe’s cast. Bind the question to a lock generation; cancel it when that lock changes; reject a stale answer without removing the queued item. Also check that the item still exists before recording “is on the big screen.”

2. **Must fix — any local process can impersonate a big-screen window.** [http.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/http.ts:847) accepts `POST` and `DELETE /api/display` from loopback without the host-window credential. A local agent or `curl` can report false screen dimensions or remove an extra screen from the room’s available screens. Require the host-window credential and change the app’s [close notification](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/screens.rs:587) to send it.

3. **Must fix — unrelated speech from a lock owner grants the brain permission to replace their screen.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:437) unlocks when *any* event in a batch comes from the owner. A batch containing Chey’s unrelated remark and Felipe’s request can therefore clear Chey’s lock; the screen tools then proceed. Require an explicit request by the owner for that screen, or an explicit answer to an unlock question. Do not infer consent from presence in a batch.

4. **Must fix — the spoken unlock check accepts negation.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:830) accepts `UNLOCK_YES` anywhere in a person’s line. The regex at [line 1420](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:1420) matches “No, don’t unlock it” and “Yes, keep mine up.” Either can clear someone else’s lock if the model calls the tool. Parse a whole, unambiguous affirmative answer tied to the pending screen request; add negative and mixed-utterance tests.

5. **Must fix — a same-owner share silently clears the owner’s lock.** [placeShare](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:321) permits the lock owner’s share, then its fallback replaces the stage with `override: true`. [setStage](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/session.ts:1523) discards the incoming lock, and [endShare](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/session.ts:1252) restores through the same method. After the share ends, the earlier cast is unlocked, contrary to SPEC 10.5’s promise that the owner retains it. Preserve the lock through the temporary share and restore, unless its owner explicitly released it.

6. **Must fix — a project switch can kill the hub before its promised save completes.** [Hub::stop](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/host.rs:204) force-kills after ten seconds. [hub.shutdown](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/hub.ts:171) can spend eight seconds on the snapshot, four on the thumbnail, and three on network shutdown; [switch_project](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:783) starts the next hub once the child exits. The ten-second limit contradicts the save sequence and SPEC’s “saves … and exits, and only then” claim. Coordinate a completion acknowledgement and make the outer deadline exceed the full shutdown budget. A timeout must be surfaced as an incomplete save, not a successful switch.

7. **Must fix — migration is not safe against two simultaneous starts.** [migrateLegacy](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:277) reads the marker without a process lock. Two starts can select the same source; both use `.<id>.partial`, and [line 323](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:323) lets one delete the other’s work. They also overwrite each other’s final marker at [line 360](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:359). The originals survive, but an import can fail or be repeated while the marker says otherwise. Serialize migration per `JAMSESH_HOME` and give each attempt private staging; test two processes starting together.

8. **Must fix — Stop hosting is outside the switch lock.** Project switches hold `state.switching` at [main.rs:783](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:783), but the menu’s `leave` path at [line 699](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:699) does not. Stop hosting during a switch can run between hub setup and window setup, stop the new hub, then have the switch open windows for that stopped hub. Put leave and its cleanup under the same serialized transition, with the public command acquiring the lock and an internal cleanup function used by a switch already holding it.

9. **Must fix — rearrangement does not verify that a window fills its display.** [screens.rs:299](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/screens.rs:299) compares only the display a window is on. If its fullscreen state or size changes while it remains on that display, the move event schedules `arrange`, but `plan` returns no action. Track window bounds and fullscreen state and reapply placement when either differs. Add a test for a resized window on the correct monitor.
