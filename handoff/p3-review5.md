## Must fix before shipping

1. **Any paired person can unlock someone else’s screen.** [http.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/http.ts:557) calls `unlockStage` without checking the lock owner; [StageControls.tsx](/Users/cheyrasmussen/jamsesh-p3/jamsesh/web/src/shared/StageControls.tsx:55) offers that button to everyone. A nonowner can clear the lock, after which the brain can replace the screen without an owner answer. Require the owner’s credential for Unlock, with any host override defined explicitly. This also conflicts with [SPEC.md](/Users/cheyrasmussen/jamsesh-p3/jamsesh/SPEC.md:1316), which says the lock stays until its owner unlocks it.

2. **An unrelated direct “yes” from the owner can clear the lock.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:874) exempts any direct owner line from the question check, while `unlockConsent` accepts bare “yes” at line 1461. If the model cites the owner’s answer to another question in `unlock_screen`, the deterministic guard unlocks. Require an explicit screen or unlock instruction, or a yes following the question about that lock.

3. **Reopen bypasses the acknowledged shutdown.** The Screen Recording setup calls `relaunch`; [main.rs](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:992) calls `app.restart()` without taking `Turns` or awaiting the hub save. The locked Tauri version permits restart without exit events on the main thread; when exit events do run, this app’s [Exit handler](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:1098) uses `try_lock()` and discards the stop result. Route relaunch through the same terminal turn and acknowledged stop as Quit, and abort relaunch if saving fails.

4. **Two starters can both take an abandoned migration lock.** [projects.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:296) checks that the lock’s PID is dead and then unlinks its path. Two processes can both pass the check; one can remove the other’s newly created live lock. Both then migrate the same home concurrently. Use an advisory lock or an atomic reclamation scheme that cannot remove a replacement lock. Test two starters against one preseeded stale lock.

5. **Queued transitions can act on stale intent.** [open_project](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:844) checks the picker before waiting for its turn, then [switch_project](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:863) starts without rechecking it. A project selection queued behind Leave can restart hosting after the person leaves. `host_here` and `join` likewise do not require an idle state when their turn arrives; [start_joining](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:291) can leave an existing host hub running. Revalidate the expected role and window inside each turn, and stop existing resources before changing roles.

6. **A vanished screen ID silently targets the main screen.** [http.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/http.ts:547) maps an explicit screen name or ID that cannot be found to `"main"` for cast, Unlock, and restore. A stale control after a display disconnect can therefore change or unlock the wrong screen. Default only when `screen` is omitted; reject an explicit unknown value as Expand already does at line 593.

Both smaller feedback fixes are present. The owner “yes” path above is a separate consent gap. First join identity remains the stated trust on pairing decision.

Delete the duplicate tile key derivation in the server and [Stage.tsx](/Users/cheyrasmussen/jamsesh-p3/jamsesh/web/src/host/Stage.tsx:91); have the server supply canonical keys with the stage while the web supplies the render nodes. It cannot catch a mounted but obscured note; use a rendered UI check.
