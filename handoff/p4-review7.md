## Must fix

1. **Recovery can revive a retired fact.** [carryover.ts](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:190) omits tombstones from `context.json`; [importJson](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:169) therefore cannot restore them. After database damage, an older session can edit a fact that was retired before recovery. [apply](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:325) sees no row and inserts it as active. Keep tombstones in validated recovery data and test this sequence.

2. **A new session misses valid context when the database is damaged.** [readProjectContext](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:223) returns `null` on a damaged newest database, even when a valid export exists. [Hub](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/hub.ts:142) seeds before the keeper can trigger write-side recovery, and never seeds again. Recover under the database lock before seeding; report a recovery failure instead of starting with empty context.

3. **A rejected concurrent edit is reported as saved and then forgotten.** [apply](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:325) can reject an older edit but records the winning row’s version in `seen`. [saveProjectContext](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:275) pairs that version with the *rejected* wording and returns `written`. The next snapshot sees no local change, so the accepted edit is never retried or surfaced. Return a per-row conflict outcome; advance `carryBase` only for applied changes and make rejected edits visible for resolution.

4. **An export failure is reported as success.** [exportJson](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:362) logs and swallows write errors after the database commits; [commitChanges](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/carryover.ts:304) still returns `written`. A later unchanged snapshot returns `skipped`, leaving the wiki’s export stale; recovery from that export can lose the committed change. Report a distinct committed-but-unexported outcome and retry export without reapplying the change.

5. **Sending a multi-agent card can silently drop an agent.** [board.ts](/Users/cheyrasmussen/jamsesh-p4/jamsesh/hub/src/board.ts:315) filters targets again but rejects only when *all* are gone. If one of two agents was removed, Send issues a one-agent directive and resolves the card. Reject the send when any selected target is invalid, leaving the card open for editing.
