## Must-fix

1. **A paired window can impersonate another device over WebSocket.** [http.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/http.ts:203) accepts the caller’s `?device=` value without checking the device’s pairing. The hub then trusts it for RTC signaling and, when the last socket using that ID closes, ends that device’s shares ([http.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/http.ts:258)). Device IDs are available in room state. A paired caller can therefore disrupt another window’s share despite the new `/shares` ownership checks. Bind the socket ID to its authenticated pairing and registered device; give host windows their own verified path. Add a cross-window WebSocket test. This is separate from the acknowledged Phase 3 person-identity issue.

2. **An initial canvas failure has no recovery path.** [canvas.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/canvas/canvas.ts:94) starts the server, then the host participant. If host startup fails, the catch only marks the canvas failed; polling and watchdog timers are installed only after success. The server can remain running, and an MCP process whose `init()` failed is not retained for cleanup ([canvas.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/canvas/canvas.ts:162)). Clean up partial startup and schedule a bounded retry even when the first start fails. Test failure at each startup step.

3. **The running canvas server’s stderr is not drained.** [canvas.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/canvas/canvas.ts:133) pipes stderr but reads it only when startup fails. Output from a healthy, long-running server can fill the pipe and block it, or accumulate without a bound. Drain continuously into a bounded diagnostic buffer and use that buffer for startup errors. Test sustained stderr output after health checks pass.

4. **The parity batch can turn unrelated shipments into one directive.** [brain.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:876) merges every shipment from the same agent within 25 seconds, regardless of feature. `coordinate_parity` also accepts multiple shippers without checking that their `seen` descriptions name the same feature ([brain.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:924)). Two unrelated visible changes can thus arrive as one cross-platform work item. Keep distinct features separate and reject a multi-shipper parity call unless their descriptions match. Test two different features shipped in one window.

5. **Extra displays can miss their six-minute return after a hub restart.** The constructor restores only the main stage’s timer ([session.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/session.ts:82)); extra-display timers exist only in memory and are created on a later `setStage` ([session.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/session.ts:1163)). A persisted, unpinned compare view can remain indefinitely after restart, contrary to [SPEC.md](/Users/cheyrasmussen/jamsesh-p1/jamsesh/SPEC.md:143). Restore each persisted display’s remaining deadline and test restart with an extra display.

## Should-fix

- **A recovered canvas still reloads on its old failure timer.** [ui.tsx](/Users/cheyrasmussen/jamsesh-p1/jamsesh/web/src/shared/ui.tsx:991) resets failure state when polling returns `live`, but leaves the scheduled rejoin at line 995 intact. Clear that timer and `retryAt` on recovery; test a failed poll followed by a live result before the retry deadline.

## Confirmation and limits

The four findings in review 5 are fixed in the pinned commit: main-display visibility follows active reports and closure; parity requires the shipping agent’s `seen`; synchronous canvas bridge throws count as failed reads; and feature deduplication checks overlap in both directions. Shipped updates are presented as information in `jam_context`, and the shipped-news pass has only `coordinate_parity` and `no_action`. The batching flaw above still permits an unrelated *parity directive*.

Nine targeted canvas-join tests passed. The hub reconnect run was inconclusive here: six tests passed and three hit sandbox temporary-directory or port errors. Child-process tests also failed in this environment; I could not establish whether those failures reproduce on a normal Mac. I did not run the 37 gateway scenarios or a live Tauri/WebRTC session, so their reported results are unverified here. No repository files were changed.
