## Production findings

1. **The wiki’s people-only write gate can be bypassed.** [http.ts](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/http.ts:33) omits `/wiki` from `HUMAN_ONLY`. At [http.ts:653](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/http.ts:653), a wiki write accepts any existing `personId` supplied in the body when there is no paired device; loopback requests are treated as locally allowed. A process on the host can therefore edit pages or create sources as a person without the host-window credential. This also bypasses approval by writing a page directly. Apply the existing human-only gate to wiki mutations and bind the actor to the authenticated window or paired person. Test an uncredentialed loopback request with a forged `personId`.

2. **An unapproved ingest can disappear at the next session.** [service.ts:263](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:263) marks sources ingested when it creates a card. The card lives in the session board, while the proposal file and ingest state live in the project vault. A new session has no board card, and `pendingSources()` excludes those sources, leaving no approval path. The restart test manually passes the old card into the new service; a real user cannot do that. Persist and restore pending project cards, or leave sources pending until resolution, and test through a new session’s board API.

3. **Transcript capture permanently skips material.** [service.ts:190](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:190) asks for 800 recent events, but [store.ts:259](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/store.ts:259) selects the *newest* 800. If more than 800 arrive between ticks, the earlier events are lost. The cursor is also saved before `addSource()` succeeds ([service.ts:194](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:194)); a source-write failure loses the batch. Finally, `flush()` uses the three-event/200-character threshold, so a short final exchange is never captured. Page forward from the oldest unprocessed event, advance only after a successful source write, and flush any remaining substantive tail.

4. **The model may replace a page using only its first 4,000 characters.** [service.ts:255](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:255) truncates existing pages before asking for a complete replacement; [service.ts:286](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:286) then stores the model’s whole replacement. A longer page can lose everything the model never saw. Approval cannot reliably catch it: [diff.ts:8](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/diff.ts:8) substitutes “too long to compare” above 700 lines and otherwise cuts the diff at 6,000 characters. Use bounded patches against the full current page, or refuse a whole-page proposal unless the entire original and complete diff are reviewable.

5. **The editor silently defeats its revision check.** [WikiView.tsx:287](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/WikiView.tsx:287) replaces `page` on wiki notifications while a draft remains in `editing`. Save then submits the refreshed `page.rev` ([WikiView.tsx:319](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/WikiView.tsx:319)). If another person edits during drafting, the draft overwrites their work without the promised conflict. Pin the base revision when editing starts; background refresh must not change it. Test two clients with the notification arriving before Save.

6. **The vault’s symlink check covers only leaf files.** [files.ts:81](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:81) follows pre-existing `wiki/` and `raw/` symlink directories, while [files.ts:215](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:215) checks only the final file. Reads and writes can escape the project folder through either parent. Reject symlinks at every vault path component, including metadata directories and files; test symlinked `wiki/` and `raw/`, not just `wiki/page.md`.

7. **Optional git history can commit unrelated project files.** [files.ts:125](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:125) runs `git add -A` in the project root. An Obsidian vault can contain user notes, settings, exports, or pre-staged work outside the wiki-owned files; JamSesh will sweep them into its commit. Stage explicit owned paths and commit only those paths, preserving unrelated staging.

8. **Acceptance is not recoverable after a partial failure.** [service.ts:341](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:341) writes pages one by one, then treats every write exception as a stale-page skip. A disk failure after the first page leaves some changes applied; a later `finish()` failure leaves the card open despite those writes. Retrying then encounters revision conflicts caused by the first attempt. Record durable per-page outcomes, distinguish revision conflicts from I/O failures, and reconcile incomplete acceptance on restart. Fault-injection tests should fail each write and `finish()` in turn.

9. **First-use migration can overwrite existing vault pages.** [service.ts:477](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:477) writes fixed slugs such as `decisions` without checking whether a person already wrote them. If migration fails before `migrated` is saved at [service.ts:493](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:493), startup repeats those writes. Make migration create-only or merge through a reviewable proposal, with durable progress across failures.

## Design concerns and nits

- The prompt-injection boundary is weaker than the tests suggest. [service.ts:318](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:318) places source text inside textual `<source>` delimiters that source text itself can spoof; `WIKI.md` is read from the editable vault and inserted into the system prompt. The output schema and approval card limit the demonstrated effect to proposals, and I found no model tool or shell execution path here. Keep authoritative ingest rules in code, pass sources as clearly separated data, and assert that injected instructions do **not** appear in proposed page content. The reported injection test only establishes that it did not create a directive or file.
- The Work tab hardcodes three aggregate slugs in [SettledLinks.tsx](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/SettledLinks.tsx:8). Fresh projects can have decision and requirement pages without those aggregate pages, leaving “What the project has settled” empty. Derive it from page categories or maintain the aggregates.
- [GraphCanvas.tsx](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/GraphCanvas.tsx:190) keeps the stage canvas repainting on every animation frame even after it settles, including with reduced motion. Delete the unconditional `|| stage`; wake it for data changes and pulses. Delete the unused `editingRef` in [WikiView.tsx:284](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/WikiView.tsx:284), or use it to protect the draft.
- The tests do not cover the failures above. In particular, the wiki UI test exercises revision conflict by submitting an old revision directly, not by receiving a wiki update while editing. The claimed git-unavailable case is also unreliable because `gitAvailable()` caches its result.

I did not run tests or launch the UI: the workspace is read-only, and these tests and browser runs create files. I could not verify browser DOMPurify behavior, crash recovery, or live model behavior. The static rendering path disables raw HTML and image fetches, but that is not a browser XSS test. Several `STATUS.md` claims about per-page approval, stale saves, and session-end ingest need revision after the fixes above.
