## Must-fix before shipping

1. **A stale unload request can close the next recording’s speech window.** [hub.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/hub.ts:368) detects that `recordingId` does not match the current recording, but calls `windowLines` anyway. That function sets `t1` on the *current* `promptMode` entry and later deletes it. Recording B survives in `recs`, while its speech window is closed by A’s late `/prompt-window` request. The [test](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/test/record.test.ts:697) checks only that B remains in `recs`. Reject a mismatched ID before touching `promptMode`, and test that B’s window remains open and collects speech.

2. **Stop can read speech outside the recording it names.** [recordStart](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/hub.ts:424) stores the caller’s `t0`; [recordStop](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/hub.ts:509) accepts any finite future `t1`. `windowLines` uses those values to select utterances. A Stop for A with a future `t1` can include B’s later words from the same device and person while it waits for transcription. Capture server-side start and stop bounds, allowing only a small documented clock tolerance. Test adjacent recordings with a future Stop timestamp.

3. **A Mac button can remain down when the helper exits.** The [Swift helper](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/native/jamsesh-live.swift:31) calls `exit` on `fail` without `releaseHeld`. Its window timer can call `fail("nowindow")` while a button is held. An `up` also clears `held` before checking whether `point()` succeeds ([line 226](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/native/jamsesh-live.swift:226)); if the window is temporarily unavailable, neither that path nor the watchdog sends an up. At the hub, a helper error sets status to `gone` directly, so [end’s early return](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/liveapps.ts:348) skips its release and cleanup. Release the stored point before every helper exit and when `up` cannot resolve a point; route helper errors through `end`. Test both failure paths.

4. **Passing a locked screen does not release its Mac tile’s button immediately.** [Session.drive](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/session.ts:1678) changes the screen’s drivers without notifying `LiveApps`; [liveapps.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/liveapps.ts:577) releases the old press only when another person sends input or the four-second idle timer fires. The screen test’s attempted pass uses a non-owner as caller and does not assert that the pass succeeded ([liveapps.test.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/test/liveapps.test.ts:566)). Release held input when the screen’s driver set or lock changes, and test a successful pass with no subsequent input.

5. **Overlapping frame-key requests can restore a stale key.** [drivetiles.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/web/src/shared/drivetiles.ts:10) lets an in-flight `withKey` request and a reconnect `refreshFrameKey` request assign the same global `frameKey` independently. A slower old response can overwrite the new hub’s key. `keepFrameCurrent` likewise lets its initial response overwrite the key remembered after reconnect ([line 39](/Users/cheyrasmussen/jamsesh-p6/jamsesh/web/src/shared/drivetiles.ts:39)). Use a request generation or one serialized refresh, and test responses completing in reverse order.

6. **The font request cap depends on Content-Type.** [http.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/http.ts:1142) enforces `FONT_BODY_MAX` while streaming JSON, then calls unrestricted `formData()` or `arrayBuffer()` for multipart and binary requests. A chunked request without `Content-Length` can make the hub buffer more than 45 MB before the route rejects its unusable body. Apply the byte cap before parsing every `/fonts/` POST body. The current [cap test](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/test/fonts.test.ts:518) covers JSON only.

7. **The build backstop never releases buttons 3 and 4.** [cleanDrive](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/http.ts:350) accepts button numbers through 4, but [devdrive’s `rel`](/Users/cheyrasmussen/jamsesh-p6/jamsesh/hub/src/devdrive.ts:48) iterates only `0..2`. A leave or timeout leaves those bits set and re-arms the watchdog indefinitely. Release every accepted button, or restrict the accepted set, and test each accepted button on leave.

8. **The checked-in end-to-end helper logs credentials.** [e2e-hub.ts](/Users/cheyrasmussen/jamsesh-p6/jamsesh/scripts/drive-e2e/e2e-hub.ts:32) prints the host-window key and paired tokens as JSON; [e2e.cjs](/Users/cheyrasmussen/jamsesh-p6/jamsesh/scripts/drive-e2e/e2e.cjs:3) reads them from a fixed log in `/tmp`. The script also imports from a hard-coded checkout path, so it cannot run from this checkout. Delete this throwaway harness or replace its credential handoff with a private, ephemeral channel and resolve imports from the repository.

9. **The native release check remains open.** [STATUS.md](/Users/cheyrasmussen/jamsesh-p6/jamsesh/STATUS.md:47) explicitly says Phase 6 is incomplete until real ScreenCaptureKit capture and CGEvent input are checked with permissions on a host. The supplied Rust test and clippy results and Swift typecheck do not exercise that behavior. Complete the documented real-host checklist before marking the phase releasable.
