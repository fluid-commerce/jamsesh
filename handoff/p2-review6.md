## Must fix before shipping

1. **A new prompt can be lost while outbox replay holds the lock.** [install-scripts.ts](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/install-scripts.ts:56) gives `queue()` about three seconds to acquire the outbox lock, then silently returns without saving the prompt. Replay holds that lock across network calls for up to a minute ([line 129](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/install-scripts.ts:129)). A prompt whose send fails during replay can therefore vanish. Keep network calls outside the shared lock, and make a failed enqueue visible and retryable. Test a failed new prompt while a slow replay is in progress.

2. **Queued prompts can cross rooms after a host switch.** The chat marker and outbox entry contain no host identity ([install-scripts.ts:27](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/install-scripts.ts:27)); replay checks only whether that session ID has joined the *current* host ([line 142](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/install-scripts.ts:142)). If a prompt was queued for room A and the person then connects the same chat to room B, replay posts A’s prompt to B. Bind markers and queued entries to a host ID and reject replay when it changes.

3. **A stale dev-server refresh can close a replacement registration.** [devproxy.ts](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/devproxy.ts:69) closes the old listener, then awaits listening and checking before storing the new generation ([line 84](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/devproxy.ts:84)). During that gap, `refresh()` still sees the old generation and can call `remove()`, which closes the new listener by the shared ID ([line 206](/Users/cheyrasmussen/jamsesh-p2/jamsesh/hub/src/devproxy.ts:206)). Registration can then publish a “live” tile with no forwarding port. Serialize refresh and registration per ID, or publish an in-progress generation before awaiting. The existing race test releases refresh only *after* registration finishes.
