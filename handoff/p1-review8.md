## Must-fix

1. **Canvas startup can leave a child process behind.** [canvas.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/canvas/canvas.ts:221) spawns `figcraft-cli`, then awaits initialization before assigning it to `this.host`. During that wait, `stop()` has no reference to close. The hub can also exit during startup before its shutdown handlers are installed ([index.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/index.ts:17)). Track the child immediately, close and reap it on Stop, and give it the same parent-death protection as the canvas server. Test Stop while MCP initialization is pending. This leaves prior review finding 4 only partially fixed.

2. **A stalled canvas relay can exhaust hub memory.** [http.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/http.ts:309) appends every incoming frame to `ws.data.queue` until the upstream WebSocket opens. There is no size limit or connection deadline; a paired client can keep sending during a stalled upstream handshake. Cap queued bytes and frames, and close the relay with a retryable error when upstream does not open promptly. This is an existing path that remains exposed during reconnect.

3. **Shipped fixes can still become parity tasks.** [brain.ts](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:1242) claims to exclude fixes, but `parityCandidate("Shipped crash fix for sidebar")` and `parityCandidate("Shipped corrected login flow")` both return `true`. With `seen` supplied, [agentUpdated](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:875) sends them to `shippedBatch`, which can create `coordinate` directives. That contradicts [SPEC.md](/Users/cheyrasmussen/jamsesh-p1/jamsesh/SPEC.md:521). Exclude fix descriptions reliably, preferably with an explicit update classification, and test these cases through the actual shipped-update path with `seen`.

4. **The inbox tells agents to finish a parity check before the required comparison.** After an agent reads a directive, a later empty [inboxText](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/mcp.ts:724) says “don’t wait for others to reply first” for *every* open directive. A [parity directive](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:944) requires the two agents to compare and confirm a gap before building. Make the reminder respect directive mode, and test a second inbox read while a parity reply is pending.

## Design concerns

- [parityTools](/Users/cheyrasmussen/jamsesh-p1/jamsesh/hub/src/brain/brain.ts:920) inserts the model’s unrestricted `feature` string into directives, and selects every online agent on the named platform without checking its product or workstream. Derive the feature label from the shipper’s `seen` text and scope recipients to the relevant app. I would delete the free-form `feature` input.

Prior findings 1, 2, 3, and 5 have corresponding code fixes: occlusion is read on the main thread, capture is single-flight per kind, socket ownership is rechecked, and the key helper has a timeout and is reaped.
