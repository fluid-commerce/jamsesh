## Must fix before shipping

1. **Quit can race a project switch and exit during the new session’s startup.** [main.rs](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:739) releases `switching` when the inner block ends, *before* awaiting `h.stop()`. A switch can then acquire the lock, find no hub in `inner`, and start another one. Quit reports the old hub’s save result and exits while the new transition is running. Hold the transition lock through the acknowledged stop and exit decision, and reject new transitions once quitting begins.

2. **A migration retry can duplicate an archived session or get stuck on `host`.** [projects.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:372) chooses a destination, publishes it at line 386, and records success only when the marker is written at line 412. If the process stops, or `writeProject` fails, between those steps, an archived source is copied again as `-copy`. For `host`, the collision check tests `sessions/host` even though the destination is `sessions/last-session`; every retry targets the occupied directory and fails. Record source provenance durably with the published session, then verify and adopt an already published copy on retry. Check the actual transformed destination for collisions.

3. **Waiting for another migration can time out and start a hub against incomplete project state.** [projects.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:299) returns old marker records after 60 seconds even while the lock owner is alive. [config.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/config.ts:124) ignores that outcome and proceeds to list or open projects while the other process is still publishing sessions. Fail startup on timeout, or keep waiting; never treat an unfinished migration as complete.

4. **A bystander’s “yes” can still unlock without being asked about the lock.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:643) opens the consent window after *any* `say_to_room` call marked `problem` following a lock refusal. It does not check that the message asked whether to replace that screen. `unlock_screen` then accepts a later plain yes at line 863. Make the lock question a deterministic, screen-specific action and record consent eligibility only after that question is delivered.

5. **Any direct request from the lock owner can clear their lock.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:448) checks who made the direct requests, but not whether they requested a screen change. If the owner directly asks JamSesh an unrelated question and the brain calls a screen tool in that pass, `lockBlock` unlocks first. Require an explicit screen-change or unlock request tied to the cited line before clearing the lock.
