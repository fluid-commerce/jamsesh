## Must fix before shipping

1. **A bystander’s “yes” can clear a different lock without answering a question.** [brain.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:443) starts a three-minute consent window as soon as a screen action is refused, before `say_to_room` asks anything. [unlock_screen](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/brain/brain.ts:845) checks only that window’s age. It does not bind it to the lock’s owner or `since` value, or require the cited line to follow the question. A later cast can therefore replace the lock while the old consent window remains usable. The [test](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/test/stage-lock.test.ts:641) treats a refused show as though a question was spoken. Record consent eligibility when the question is actually asked, bind it to that lock generation, and invalidate it on every lock change.

2. **Quit can report success before the session saves.** During a project switch, [main.rs](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:789) removes the hub from `inner` while its stop runs. The [Exit handler](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:1017) uses `try_lock` and stops only a hub still in that slot; it neither waits for the switch nor reports its result. Worse, if the parent disappears during shutdown, a second call to [shutdown](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/index.ts:103) immediately calls `process.exit(0)` when `stopping` is true, potentially cutting off the save and falsely signalling completion. Make repeated shutdown calls wait for the first result, and keep app exit behind the serialized, acknowledged stop.

3. **A live migration loses its exclusive lock after ten minutes.** [projects.ts](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:311) declares a lock abandoned by age before checking whether its PID is alive. A second startup can remove the lock of a legitimate large migration and start another; the first then unconditionally removes the second process’s lock at [line 304](/Users/cheyrasmussen/jamsesh-p3/jamsesh/hub/src/projects.ts:304). Check liveness first and release only a lock still owned by that attempt. Test two processes with a live, old lock.

4. **The resized-window placement fix has no resize trigger.** The planner now compares frames, but [main.rs](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:925) schedules arrangement only for `Moved` and `Destroyed`. [screens.rs](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/screens.rs:573) watches display changes, not window size. A big-screen window resized in place can remain the wrong size indefinitely. Handle `Resized` through the same debounced arrangement path.

5. **Failed initial launches leave active state behind.** [start_hosting](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:180) stores the hub and host role before fallible window and screen setup. [host_here](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:747) returns those errors without cleanup; [join](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:821) similarly leaves its relay and saved join role if window creation fails. The project-switch path has cleanup, but initial hosting, joining, and resume do not. Roll back each failed transition under `switching`, stopping its hub or relay and restoring a usable start state.

## Design and smaller issues

- [App::save](/Users/cheyrasmussen/jamsesh-p3/jamsesh/app/src-tauri/src/main.rs:92) ignores directory, serialization, and write errors and writes `app.json` in place. A failed or interrupted write can silently change what relaunch opens. Return errors and use an atomic replacement.
- [expandTile](/Users/cheyrasmussen/jamsesh-p3/jamsesh/web/src/host/Stage.tsx:141) discards every API error, so a failed Expand or Collapse has no explanation. Route it through the existing `stageAction` feedback.
