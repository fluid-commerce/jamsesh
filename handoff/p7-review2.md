## Production findings

1. **Must fix — large sources are silently marked read after partial ingest.** [service.ts:314](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:314) sends at most 60,000 characters of a source to the model, while [files.ts:440](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:440) stores up to 200,000. The card and ingest state track the whole source ID, so accepting, dismissing, or receiving no proposal permanently skips its unread tail. Split sources into durable, offset-tracked chunks and mark each chunk handled only after it is read. Test a fact that appears solely after character 60,000.

2. **Must fix — an approval can overwrite a person’s edit made during the model call.** [service.ts:337](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:337) snapshots page text, then awaits the model. [service.ts:383](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:383) reads the page again and records *that later revision* as the proposal base. If someone edits in between, the model’s replacement was written from old text but passes the acceptance revision check at [service.ts:524](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:524). Carry the revision with the text shown to the model; reject or regenerate an output when it has changed.

3. **Must fix — source creation is not atomic.** [files.ts:451](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:451) writes directly to the final `raw/*.md` path. A partial write followed by an I/O error leaves a file that [files.ts:480](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:480) enumerates as a source; `readSource` can even treat a damaged header as document text. Write to an exclusive temporary file, rename after a complete write, and remove failed temporary files. Fault-inject a partial source write.

4. **Must fix — automatic agent updates can disappear.** [service.ts:201](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:201) catches every failure while saving a shipped or decision update and returns `null`. [service.ts:281](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:281) also excludes those updates from transcript capture, leaving no retry path. Keep a durable pending update or include the event in cursor-backed capture; test source-write failure followed by recovery.

5. **Must fix — acceptance finalization is not retry safe.** [service.ts:175](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:175) appends the log before rebuilding the index. If index writing fails, retry appends the same acceptance again; the existing fault test at [wiki.test.ts:677](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/test/wiki.test.ts:677) checks the pages and index but not the duplicate log. There is also a crash window after [service.ts:547](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:547) removes the proposal and marks its sources ingested, before [board.ts:335](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/board.ts:335) closes the card. That leaves an open, unacceptably expired card after restart. Make finalization idempotent with a durable acceptance phase and reconcile it on startup; assert one log entry and a resolvable card after failures at each boundary.

6. **Must fix — filing an answer can lose its approval proposal.** [service.ts:605](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:605) creates an answer source and [service.ts:607](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:607) marks it ingested *before* creating the card. A crash or proposal-write failure between those steps leaves no pending source and no card. Keep it pending until the proposal is durably raised and resolved.

7. **Must fix — the approval UI still conceals part of a deletion.** The backend now produces deletion counts and a tail notice, but [WikiCard.tsx:92](/Users/cheyrasmussen/jamsesh-p7/jamsesh/web/src/wiki/WikiCard.tsx:92) silently shows only the first 400 diff lines. A reviewer can accept a large removal without seeing the remaining lines or the backend’s “more lines removed” notice. Show the complete diff, or make truncation explicit and provide a full review view. Test a deletion beyond line 400.

8. **Must fix — host wiki actions need an identified person.** [http.ts:658](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/http.ts:658) permits a host window with no selected person to edit pages and add sources, attributing them to “the host.” The wiki card route has the same exception at [http.ts:675](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/http.ts:675). This breaks the specified person-attributed edit and approval log. Require a real session person for these mutations, including host windows, and test an authenticated host window before person selection.

## Design concerns

- **Should fix — finish the fact-list transition.** The UI has moved to wiki pages, but [board.ts:223](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/board.ts:223) still saves direct “remember this” items as facts, and [mcp.ts:903](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/mcp.ts:903) still reads facts for agent context. The spec acknowledges this exception. It leaves two stores for settled knowledge. Make those writes wiki sources or pages, then delete the legacy fact read/write path once migration is complete.
- **Should fix — tag the whole ingest data block.** [service.ts:88](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:88) places people, workstream names, and the wiki index outside the random data tags. Titles and summaries in the index are editable content. Tag these fields too and test whether an injected index title appears in proposed text. I found no model tool or shell access in this path; the demonstrated exposure is proposal integrity.
- **Should fix — preserve edit-source integrity on an uncertain page write.** [service.ts:568](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/service.ts:568) deletes the edit source on *any* `writePage` exception, although [files.ts:357](/Users/cheyrasmussen/jamsesh-p7/jamsesh/hub/src/wiki/files.ts:357) can rename the page successfully and then fail on its read-back. Re-read the page before deleting the source; retain a recovery record if the outcome is uncertain.

## Round-one audit and limits

The people-only route gate, cross-session proposal restoration, forward transcript cursor, full-page model input, pinned editor revision, symlinked directory rejection, explicit Git paths, create-only migration, category-based Work links, and idle graph stop are present. The full-diff, retryable-acceptance, and actor-attribution claims remain incomplete for the reasons above. Random tagging covers source bodies and pages, but not all ingest inputs.

Static tracing found no direct route from an unapproved proposal into `jam_join` or `jam_wiki_*`: those read accepted `wiki/` pages. The Markdown path disables raw HTML and image fetches and runs DOMPurify. I could not verify browser XSS behavior, live model behavior, power-loss recovery, or the absent `craftrules/AGENTS.md` at the documented relative path. I did not run tests or launch the UI because they create files in this read-only review; `git diff --check` passed.
